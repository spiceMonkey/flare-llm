Decode Modeling

Framework Overhead Model: Per-Phase Latency Constants

Author: Yue Lu
Date: April 2026

The hardware roofline model in decode.md establishes a lower bound on per-token decode latency, governed by compute throughput and HBM bandwidth. Real serving systems, however, introduce additional latency above this bound that lives entirely on the host CPU and serving-software path: tokenization at request entry, request scheduling and batch assembly, token sampling, and response streaming. These are empirical constants that require profiling on the target system — they cannot be derived from hardware specifications alone. This document catalogs the CPU / software-stack overhead terms, explains where each comes from, defines the per-request framework overhead tframework​ and shows how it enters time to first token (TTFT) and the latency of a whole request (§3), and lists the constants that describe each serving stack in the decode step itself, with the status of every value (§4). The kernel-launch and host-work terms that those constants feed are derived in decode.md §7; this document does not repeat the derivation. Hardware-level overheads tied to the network fabric (the transfer of a key-value (KV) cache between a prefill pool and a decode pool) are covered in disaggregation.md; memory-traffic calibration constants live in decode.md §6.2.

Two derivations cited below are companion documents that are not chapters of this book: the prefill and TTFT derivation, and the end-to-end metrics derivation. They are cited as plain text.

2. CPU / Software-Stack Overhead Terms

Each subsection below describes what the term measures, why it exists at the systems level, how to calibrate it on a target deployment, and typical values from published sources where available.

2.1 Tokenization Latency

What it measures. ttok​ is the wall-clock time from receiving a raw text request to the point where token IDs are ready and the first CUDA kernel for the prefill pass is launched. It includes byte-pair encoding (BPE) or SentencePiece lookup, Unicode normalization, and any pre-processing applied by the serving framework.

Why it exists. Tokenization runs on CPU in most serving stacks (vLLM, TensorRT-LLM, TGI). While GPU-side tokenization libraries exist, they are not universally deployed. The CPU→GPU handoff itself adds a small scheduling gap.

Scaling behavior. ttok​ scales weakly with input length: roughly O(Sinput​) character-level operations, but constant factors are small (BPE lookup is table-driven). For Sinput​≤4096 tokens the cost is typically 0.1–2 ms and is often pipelined with the previous request’s decode tail.

Calibration. Measure the latency from HTTP request receipt to the timestamp of the first cudaLaunchKernel call in a profiler trace (e.g., Nsight Systems). Vary Sinput​ to isolate the length-dependent component.

Typical values. 0.1–0.5 ms for short prompts (Sinput​≤512); up to 2 ms for very long prompts (Sinput​≈8192) on a single CPU thread. Parallelizing tokenization across CPU threads or pipelining it with KV allocation reduces the effective contribution to near zero for batch serving.

2.2 Request Scheduling and Batch Assembly

What it measures. tsched​ is the time the serving scheduler spends admitting one request: taking it from the queue, checking that its KV cache fits, allocating its KV pages, and preparing its batch metadata (token IDs, position IDs, block table) so that its prefill pass can launch. It is paid once per request, on the way in, and is part of TTFT (§3).

Why it exists. Before a request’s first kernel can launch, the scheduler must:

  1. Take the request from the priority queue of waiting requests.
  2. Estimate whether its KV cache pages fit in available HBM.
  3. Run the PagedAttention block allocator [VLLM] to assign physical KV blocks.
  4. Optionally, plan chunked-prefill piggybacking [SARATHI] for the request.
  5. Construct the attention metadata (block tables, sequence lengths) needed by the kernel.

All of this runs on CPU and must complete before the GPU kernel can launch.

What it is not. Continuous batching also makes the scheduler run between every two decode steps: it re-evaluates the active set, retires finished sequences and refreshes block tables. That recurring work is not tsched​. It is the per-step host work tstep,seq​(B)=corch​+cseq​⋅B of decode.md §7.3, which is charged on every decode step inside tstep,user​ and whose constants are listed per stack in §4. Keeping the two apart avoids charging the same work twice: tsched​ is the one-off admission of a request, tstep,seq​ is what the request costs the host on each step while it is active.

Calibration. Instrument the admission path with timestamps from request dequeue to the launch of its first kernel. Vary the number of concurrently active requests and the scheduler policy (first-come-first-served, preemptive, chunked prefill) to characterize the dependence on load.

Typical values. 10–50 µs under light load with simple first-come-first-served admission; 50–200 µs under heavy load (B≥64 active sequences) with full PagedAttention block allocation and chunked-prefill planning.

2.3 Response Streaming and Detokenization

What it measures. tdetok​ is the per-token cost of converting the sampled token ID back to a UTF-8 string fragment and transmitting it to the client (via HTTP chunked transfer or server-sent events).

Why it exists. Detokenization is the inverse of tokenization: a table lookup from token ID to byte sequence. It runs on CPU and is followed by a streaming write to the network socket. For most vocabulary sizes, the lookup itself is negligible; the dominant cost is the system call for the socket write plus any interpreter overhead in the serving framework.

Scaling behavior. tdetok​ applies once per generated token and is effectively constant in token output length (it does not grow with Tout​, only accumulates). The cumulative detokenization cost is Tout​×tdetok​, which is small relative to the total decode time for any non-trivially sized model.

Calibration. Measure round-trip latency from GPU token ID to client receipt at the application layer, minus network round-trip time (RTT). The residual is approximately tdetok​ (the sampling kernel after the LM head is folded into tLM,hw​ on the GPU side, not into this term).

Typical values. ~1–10 µs per token for the detokenization lookup itself. Socket write latency varies with network configuration and is separate from this constant.

3. Total Framework Overhead Per Request

Combining the CPU / software-stack overhead terms of §2, the framework’s share of a complete request — a prefill pass followed by decode steps, Tout​ output tokens in all — is:

tframework​=ttok​+tsched​+Tout​⋅tdetok​

The first two terms are paid once per request, the third once per output token. Kernel-launch dispatch and per-step host work are not in this sum — they are inside tstep,user​ (decode.md §7.1, §7.3). The LM head matrix multiply and the sampling kernel are likewise GPU-side and absorbed into tLM,hw​ inside tstep,user​ (decode.md §7.2).

Where the two per-request terms sit. Tokenization and scheduling happen before the prefill pass, so they are part of TTFT:

TTFT=tsched​+ttok​+tprefill​+tafter​

Here tprefill​ is the hardware prefill time (derived in the companion prefill document), which ends with the LM head on the last prompt position and therefore already yields the first token. When a prefill replica runs several prompts in one pass, every one of them waits for the whole pass, so tprefill​ is the time of the batched pass. tafter​ is whatever stands between the end of prefill and the emission of that token, and depends on who emits it:

Deploymenttafter​
Prefill and decode on the same replicathe repack of the cache into the decode layout, thandoff​; zero when the two phases use the same partition
Separate pools, the decode worker emits the first tokenthandoff​+tstep,user​: the decode worker waits for the cache, re-runs the last prompt position as one decode step, and emits the token
Separate pools, the prefill worker emits the first tokenzero; the transfer delays the second token instead

thandoff​ and the two-pool cases are derived in disaggregation.md.

Whole-request latency. The first token is the product of the prefill pass, so the remaining Tout​−1 tokens each take one decode step, and every token is streamed once:

ttotal​=TTFT+(Tout​−1)⋅tstep,user​+Tout​⋅tdetok​

In the third deployment of the table the handoff, which is not on the TTFT path, is added once (it lengthens the gap between the first and the second token). Because ttok​ and tsched​ are already inside TTFT, tframework​ must not be added on top of this expression: doing so would count tokenization and scheduling twice. Written with the framework’s share separated out, the same total is

ttotal​=(tprefill​+tafter​)+(Tout​−1)⋅tstep,user​+tframework​

The time per output token reported by the model is tstep,user​ alone; the streaming cost tdetok​ is reported beside it as a separate per-token figure and is not folded into it.

Order-of-magnitude comparison. For a representative decode-heavy workload (Tout​=512, greedy sampling, prefill and decode on the same replica):

TermPer-stepCumulative (Tout​=512)
tstep,user​ (hardware plus the kernel-launch budget and per-step host work of decode.md §7, and tLM,hw​)~2–20 ms1–10 s
tdetok​~5 µs~2.5 ms

The three terms of tframework​ are typically well under 1% of total request latency for well-optimized serving stacks on large models. The software stack’s larger contribution is inside the decode step, through the constants of §4.

4. Per-Stack Constants of the Decode Step

decode.md §7 turns the hardware stage time into the user-observed step time with two host-side terms: the kernel-launch dispatch budget of a stage, tstage,kernel​, and the per-step host work, tstep,seq​. Both are built from a handful of constants that describe the serving stack — the software that runs the model — and not the model, the hardware or the workload. This section lists them and gives the value used for each stack.

4.1 The Five Constants

ConstantMeaningEnters
τlaunch​Effective time to launch one GPU kernel (launch time)tstage,kernel​=τlaunch​× (kernels launched per stage pass), decode.md §7.1
ρkernel​Launch overlap: fraction of the stage’s hardware time behind which kernel dispatch hides, in [0,1]tstage,hw​+max(0,tstage,kernel​−ρkernel​⋅tstage,hw​), decode.md §7.2
cseq​Host work per active sequence per steptstep,seq​(B)=corch​+cseq​⋅B, decode.md §7.3
corch​Host work per step that does not depend on batchsame
ρseq​Host-work overlap: fraction of the per-step hardware window behind which host work hides, in [0,1]tstep,base​+max(0,tstep,seq​−ρseq​⋅tstep,base​), decode.md §7.3

An overlap of 1 means the host runs ahead of the GPU and its work costs nothing until it exceeds the hardware time it hides behind; an overlap of 0 means the two add. The kernel count that multiplies τlaunch​ uses the same three fan-out numbers for every stack: kcompute​=10 compute kernels per layer, kcollective​=2 kernels per collective call, and kpp_hop​=2 kernels per inter-stage hop. Because the count is the same flat figure everywhere, τlaunch​ is an effective launch time: it absorbs kernels that a captured graph does not cover and layers that launch more kernels than the flat count assumes (Mixture-of-Experts (MoE) layers in particular).

Reading the table:

  • Launch time. 1.5 µs is what graph replay costs when every kernel is inside the captured graph. The orchestrated compiled runtime sits at 4 µs, between that and the measured eager-mode floor of about 4.5–4.7 µs per launch [TAXBREAK], because expert routing and the per-step scheduler path stay outside the graph and MoE layers launch several times more kernels than the flat count. The interpreter-based runtimes keep 8–12 µs even under an orchestrator: the orchestrator absorbs per-sequence host work but does not remove the interpreter from the dispatch of kernels that fall outside the graph.
  • Launch overlap. 1 for the graph-replayed stacks, 0.3 for the two interpreter-driven ones, whose interpreter stalls prevent the host from running ahead. No stack description uses 0.
  • Host work per sequence. One value, 5 µs, for the three orchestrated stacks; 40 µs for the interpreter-driven stacks; 75 µs for the raw compiled runtime, which runs its per-sequence loop on the host between forward passes without an orchestrator to absorb it.
  • Host work per step. Zero in every stack description. It is non-zero only where it has been fitted to a measured setup (§4.3).
  • Host-work overlap. 1 for the graph-replayed stacks, 0 for the interpreter-driven ones.

Only two rows rest on measurement, and only for the constants named in their status. Every other value is a starting point to be replaced when the setup at hand is measured.

4.3 Calibration Is per Setup

A setup is one model on one system under one serving stack. The table of §4.2 is what the model uses for a stack before any measurement of the setup exists. When measured points of a setup are available, a few constants are fitted to them, and those fitted values replace the table’s values for that setup only.

What is shared and what is fitted:

  • Shared by the setups of a stack: the launch time τlaunch​, and the rule for whether host work hides behind the GPU step (ρseq​).
  • Fitted per setup, at most four constants: a multiplier on the sustained memory-bandwidth factor ηβ​ of decode.md §6.2; the per-sequence host work cseq​; the per-step floor corch​; and the launch overlap ρkernel​.

The fitted values show how far a setup can sit from its stack’s row. For the orchestrated compiled runtime on a rack-scale system, two setups (a 120-billion-parameter MoE model and a 671-billion-parameter MoE model with latent attention) return cseq​ of 5.5 and 4.8 µs, corch​ of zero and 0.62 ms, and ρkernel​ of 0.55 and 0.35, against the row’s 5 µs, zero and 1. For the raw compiled runtime on single-node systems, three setups return cseq​ of 49–85 µs and corch​ of 1.25–4.15 ms, against the row’s 75 µs and zero. In all of these fits the host work adds to the GPU step (ρseq​=0) rather than hiding behind it, although the stack rows carry ρseq​=1: on the measured setups the graph-replay assumption that the host runs ahead of the GPU is the optimistic end.

Three rules follow.

  1. Treat the fitted constants as residuals, not as measured properties of the software. They close the gap between a first-principles hardware model and a measurement, and they take up whatever the hardware model leaves out (§4.4).
  2. Do not carry a fit from one model to another. Constants fitted on one model and applied to a different model on the same hardware and stack leave errors several times larger than the fitted error. Report the error on points that were held out of the fit beside the fitted error.
  3. A stack row is a prior. For a setup that has not been measured, the row gives the right order of magnitude for a compiled, an orchestrated or an interpreter-driven stack, and no more.

4.4 What the Fitted Constants Absorb

The hardware model drops or omits a few effects, and none of them has a correction term of its own:

  • Residual activation traffic (decode.md §2.2): the hidden-state and feed-forward-network (FFN) buffer reads and writes that remain once the attention score matrix is kept out of device memory. On a measured setup it is absorbed by the fitted memory-bandwidth multiplier.
  • Normalization and elementwise compute (decode.md §3.4): absorbed by the sustained compute rate of the device and, at small batch, by the host constants.
  • Preemption, swap and recompute of a running sequence’s cache (kv.md §4.3): not modelled. A deployment that preempts is outside the steady state the step-time model describes; the cost of moving a cache to host memory and back, and of recomputing it instead, is priced in disaggregation.md.

The first two are the reason the fitted constants are residuals. The third is a limit of scope, not something a constant can absorb.
