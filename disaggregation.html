Decode Modeling

Phase and Memory Disaggregation: Pools, Transfers, and Warm Memory

Author: Yue Lu
Date: November 2026

Keywords:
prefill–decode disaggregation, KV cache transfer, pool sizing, prefill interference, prefix reuse, warm memory, CXL, host memory, time to first token, throughput per GPU, large language model (LLM) inference

Abstract

A serving deployment can be split in two independent ways. Phase disaggregation runs prefill and decode on separate pools of devices and moves each request’s key-value (KV) cache between them. Memory disaggregation keeps caches that are not being decoded outside the accelerators’ own memory, in host memory, and brings them back when they are needed. This document derives the steady-state, closed-form cost of both on top of the decode model (decode.md) and the prefill model (prefill.md), neither of which it changes. It introduces one transfer function for every move of a cache, sizes a prefill pool and a decode pool, prices the interference a shared pool suffers, prices prefill on a cached prefix, and counts the sessions that host memory lets a deployment hold. Queueing delay, the prediction of cache hit rates, and eviction policy are outside its scope: where they matter they enter as inputs.

1. Hot Memory and Warm Memory

Memory is divided by one question: does the decode step read it? Hot memory is the accelerator’s own memory, for a graphics processing unit (GPU) its high-bandwidth memory (HBM), and every decode step reads the weights and the whole cache of every running sequence from it (decode.md §2). Warm memory is host memory, either dynamic random-access memory (DRAM) or memory attached over Compute Express Link (CXL), and it is read only when a cache moves between it and the accelerators.

The division is forced by bandwidth. Suppose the cache of the B running sequences sat in a memory that delivers BWw​ bytes per second into one device. The step would then need at least

tmem​≥BWw​B⋅TKV,token​​

where TKV,token​ is the per-device, per-sequence cache read of decode.md §2.3. Bytes in host memory reach an accelerator through the host’s root complex and a Peripheral Component Interconnect Express (PCIe) link. Two measurements of copies from CXL memory into GPUs put the rate of that path at tens of gigabytes per second: 26 GB/s for GPU reads from a CXL memory pool in [BELUGA], which attributes the limit to the root complex, and about 47 GB/s in total into the eight GPUs of one host in [SAMSUNG-CMMD]. This document uses that range for any host memory; for plain DRAM it is an assumption and not a measurement. HBM delivers several terabytes per second to one device. The ratio is two to three orders of magnitude.

Worked case. Llama-3.1-70B at 16-bit precision on eight H200 GPUs (141 GB of HBM each, at 4.8 TB/s) with tensor parallelism (TP) of 8, a context of 32,768 tokens and a batch of 16. The cache of one sequence is 10.74 GB, so one device reads 16×10.74/8=21.5 GB of cache per step. At a per-device share of the host path of 3.25 to 5.9 GB/s (26 or 47 GB/s over eight GPUs) that read takes about 3.7 to 6.6 s. The whole step, weights included, takes 14 ms from HBM.

The consequence is the rule the rest of this document follows. Weights and the cache of a sequence that is being decoded are hot and are priced by the decode and prefill models. Everything warm is priced only when it moves, and it changes three results: the time to first token (TTFT), the accelerator time a request spends in prefill, and the number of sessions a deployment holds. It does not change the time per output token (TPOT) of a running step.

Warm memory therefore absorbs overflow in time, meaning the caches of idle sessions and prefixes that may be reused. It does not absorb overflow within a step: a set of running sequences whose caches exceed hot memory cannot be served from it.

Cold storage, local flash or a remote store, is described the same way as warm memory and differs only in its numbers: a longer latency to the first byte, a write rate of its own and, for a remote store, a network stage in its path (§8).

2. One Transfer over a Path

Every move of a cache is the same operation: M bytes travel over a path, an ordered chain of stages. A stage is described the way a switch tier of a network fabric is described in decode.md §5: a number of parallel ports ni​, a rate per port BWi​ and a latency αi​. The stage latencies add and the bytes move at the slowest stage:

tmove​(M)=i∑​αi​+nblk​⋅τblk​+mini​ri​M​

ri​={ni​⋅BWi​ηbusy​⋅ni​⋅BWi​​hardware stagehost side stage​

This is the same reduction of a chain to a total latency and a minimum bandwidth that the network model applies to a collective that crosses several fabric tiers, and it is the latency-plus-bandwidth form of [ALPHA-BETA] with the bandwidth taken at the bottleneck.

What the port count means. The ports of a stage are counted per host, per receiving device, or as a fixed number. A root complex is taken as one per host (a two-socket host has one per socket, and the measured rate is then the total of the host), so a replica that spans nh​ hosts has nh​ of them in parallel, and a replica that uses only part of a host (nh​<1, §8) has that fraction of the host’s rate. A PCIe link is one per device, so a replica of g devices has g. A set of CXL devices or of links between two pools is a fixed number.

Host-side stages are measured. The rate of the root-complex stage is a per-platform measurement and not a derating of the link rate. The links of an eight-GPU server add up to several hundred gigabytes per second, while the measured rates are 26 GB/s in [BELUGA] and about 47 GB/s into eight GPUs in [SAMSUNG-CMMD]. The stage is therefore the bottleneck, and it carries its own parameter.

Calibration terms. Three terms are neutral by default and exist so that a measurement can be fitted without changing the formula.

  • ηbusy​∈(0,1] is the extra loss of the host-side stages while the host’s processors are busy serving. It multiplies only those stages, so it has no effect on a path whose bottleneck is hardware.
  • τblk​ is a processor cost per cache block moved, charged nblk​=⌈M/Mblk​⌉ times. It is the analogue of the per-request posting cost τWR​ of prefill.md §6.4.
  • A copy that is stored whole at each stage before the next begins pays every stage in turn, so the last term becomes M∑i​1/ri​; a streamed copy pays only the slowest stage. Which of the two applies is a property of the software path.

A measurement of transfer time against cache size is a straight line. Its intercept identifies the latency and its slope the delivered rate; the two remaining terms need a second experiment each (load on the host, and block size).

3. The Handoff as a Transfer

The handoff of prefill.md §6.4 moves a finished cache from a prefill replica to a decode replica. It is one use of §2, and five refinements follow from treating it that way.

Direct or staged. A transfer by remote direct memory access (RDMA) that writes into accelerator memory does not pass through host memory, and its path is the link between the pools alone. A transfer that lands in host memory first and is then copied to the accelerators has the host stages of §2 appended to its path. The distinction matters by a large factor: the transfer engine of [MOONCAKE] is reported at 190 GB/s over eight 400 Gb/s links, four to seven times the measured host path. A direct handoff must not be capped by the host path; a staged one is.

Parallel streams. When every device has its own link, each device pair ships its own shard and the first stage has

nstreams​=min(gp​,gd​)

ports, where gp​ and gd​ are the devices of one prefill and one decode replica. The rate per port stays the delivered rate BWinter​ of prefill.md §6.4, a calibrated number: the two rates reported for the transfer engine of [MOONCAKE], 87 GB/s over four 200 Gb/s links and 190 GB/s over eight 400 Gb/s links, are 87% and 48% of the line rate, so the delivered fraction is not a constant.

Repack only when the layouts differ. A replica splits one sequence’s cache by layer across its pipeline stages, by head across its tensor-parallel group, and by position across its sequence-parallel group. Its layout is the triple (PP,Dkv​,SP) of notation.md §1, where PP and SP are the pipeline-parallel and sequence-parallel factors, with Dkv​=1 for a latent cache under tensor-parallel attention, because that cache is not split by head (attention.md §3). The repack term trepack​ of prefill.md §6.4, like the layout transition of §6.3, applies when the two replicas’ layouts differ and is zero when they are equal. Expert parallelism does not enter: an expert group holds whole sequences, so it decides where a cache lives and not how it is split.

A residual that overlap cannot remove. With layer-wise streaming the transfer overlaps prefill by a fraction ρKV​ of the prefill time. The last layers still ship after prefill ends: [SPLITWISE] measures a constant non-overlapped time of about 8 ms on A100 and about 5 ms on H100 GPUs. Writing tresid​ for that residual and tserial​=tmove​(MKV,total​)+trepack​ for the un-overlapped handoff,

thandoff​=max(min(tresid​,tserial​),tserial​−ρKV​⋅tprefill​)

The inner minimum keeps the floor from exceeding the transfer itself, which matters for short prompts. With tresid​=0 and a path of one stage at BWinter​ this is the expression of prefill.md §6.4.

Caches in flight. A cache that is arriving at a decode replica occupies hot memory before its sequence is decoded. It does so from the first byte of the transfer, so the time it is held is the part of the transfer that overlaps prefill plus the handoff that follows. With λrep​ requests per second reaching one decode replica, the mean number in flight follows from Little’s law [LITTLE]:

Nfly​=λrep​⋅(thandoff​+ρKV​⋅tprefill​)

Without overlap this is the rate times the whole transfer. The count takes memory as reserved when the transfer starts, which is the upper bound: an allocator that grows with the arriving bytes holds about half of it. Time spent waiting for a decode slot is not included. Each cache in flight takes the room of one resident sequence’s cache, which lowers the number of sequences the replica can hold (kv.md §6).

4. Two Pools

A pool is a set of identical replicas, each of which completes requests at a fixed rate. Let tprefill​ be the time one prefill replica takes for a batch of Bpf​ prompts of length Sinput​, and let a decode replica run B sequences that each generate Sout​ tokens. The service rates in requests per second are

μp​=tprefill​Bpf​​μd​=Sout​⋅TPOT(B)B​

One request therefore costs cp​=gp​/μp​ device-seconds of prefill and cd​=gd​/μd​ device-seconds of decode. Two results follow without a request rate. With Gp​ and Gd​ the total devices of the two pools, the pools are balanced, meaning both serve the same request rate, when their device counts are in the ratio of those costs, and the throughput per GPU (Tput/GPU), the output rate per device, counts both pools:

Gd​Gp​​=cd​cp​​Tput/GPUboth​=cp​+cd​Sout​​

The throughput per GPU of e2e.md §5.1 is Sout​/cd​: it counts the decode devices only, which makes the prefill pool look free. The two differ by the factor 1+cp​/cd​.

Batch and replica size. Every prompt of a prefill batch waits for the whole pass, so tprefill​ here is the time of the pass over Bpf​ prompts, and it is also the prefill term of time to first token. Using the time of one prompt alone would overstate μp​ by up to a factor of Bpf​, because a compute-bound pass over Bpf​ prompts takes close to Bpf​ times as long as a pass over one. The replica sizes gp​ and gd​ are the devices of one replica of each pool: the product of the pipeline, tensor, expert and sequence parallelism factors when tensor and expert parallelism use separate devices, and with max(TP,EP) in place of TP⋅EP when a stack co-locates them on the same devices.

Given an offered rate λ and a utilisation cap u∈(0,1] that leaves headroom for queueing, the whole number of replicas in each pool is

Np​=⌈u⋅μp​λ​⌉Nd​=⌈u⋅μd​λ​⌉

The ratio of prefill to decode workers is an output of this section and moves the way the systems literature reports: up with the prompt length and down with the output length. Published deployments span roughly an order of magnitude, from more decode than prefill workers to nine prefill workers per decode worker ([DISAGG-PREFILL], [SPLITWISE], [MOONCAKE], [DYNAMO]); those figures come from other models, hardware and workloads, so they bound the plausible range and are not fitted.

5. Interference in a Shared Pool

A shared replica runs both phases on the same devices. It is modelled as time-sliced: while a prefill pass runs, the decode steps of the sequences already in progress wait. This is the interference that motivates disaggregation in [DISAGG-PREFILL], and it is absent from the roofline of either phase.

With λrep​ requests per second on one replica, the fraction of wall-clock time spent in prefill, the mean time per output token and the worst gap between two tokens are

d=λrep​⋅Bpf​tprefill​​TPOTshared​=1−dTPOT(B)​tgap,max​=TPOT(B)+tblock​

where tblock​ is the longest wait one prefill imposes: the whole pass, or one chunk when prefill is chunked (prefill.md §5). Chunking shortens the worst gap and moves the mean only by the difference between the chunked and the unchunked prefill time.

The replica is full when its B decode slots are all occupied, which happens at

λmax​=Bpf​tprefill​​+BSout​⋅TPOT(B)​1​

Below λmax​ fewer than B sequences are running, so evaluating the step at B throughout is conservative; the batch itself is swept when a deployment is sized.

Sharing and splitting tie on mean throughput. A shared replica of g devices at λmax​ produces Sout​⋅λmax​/g tokens per second per device. Multiplying the denominator of λmax​ by g gives cp​+cd​ of §4 with gp​=gd​=g. So with the same replica shape in both pools and a handoff that costs no device time, a shared pool and a balanced split have exactly the same mean throughput per device. Disaggregation gains in three places only: the worst gap between tokens, a different shape or different hardware for each phase, and the batch that a latency target allows.

The gain inside a latency target. Under a target T∗ on the mean time per output token, a shared replica must keep TPOT(B)/(1−d)≤T∗, which caps its prefill duty and therefore its request rate:

λrep​≤min(λmax​,(1−T∗TPOT(B)​)⋅tprefill​Bpf​​)

A decode pool is not interrupted, so it only needs TPOT(B)≤T∗. Each deployment picks the batch that serves it best. For the worked case of §1 with an 8,192-token prompt and 512 output tokens, with each deployment choosing among every batch that fits in memory (up to 368 sequences), the split serves 1.14 times the throughput per device of the shared replica at a 50 ms target, 1.25 times at 30 ms, 1.43 times at 20 ms and 2.03 times at 12 ms. A target on the worst gap excludes the shared replica altogether once the target is below one prefill pass or one chunk.

6. Prefill on a Cached Prefix

When the cache of the first P tokens of a prompt is already present, only the remaining C=Sinput​−P tokens are prefilled. The new tokens attend to every position of the prompt. The chunked model of prefill.md §5 charges each query a whole tile of positions, so that its chunks sum to the unchunked attention work; under the same convention a suffix of C tokens after a prefix of P is charged 2P+C positions per query. Per layer, before sharding,

Fattn,suffix​=4⋅C⋅(2P+C)⋅H=4H((P+C)2−P2)

which is exactly the attention work of the whole prompt less that of the prefix. Consecutive suffixes therefore sum to the unchunked figure, and a suffix on an empty prefix is the whole prefill. The suffix is priced as one chunk for a prefix of any length:

  • Compute. The linear work of C tokens plus Fattn,suffix​, sharded as in prefill.md §1.5.
  • Memory. The weights once, the cache write of C entries, and the cache read of the P entries the suffix attends to.
  • Communication. The stage’s collectives evaluated at C tokens per step.

With tstage,suffix​ the resulting stage time and tLM​ the output projection on the last position,

tsuffix​(P,Sinput​)=PP⋅tstage,suffix​+tLM​

The suffix is priced for a single request, as the chunked model is.

7. Prefix Reuse with a Hit Rate

A request whose prefix is cached in warm memory fetches it and prefills the suffix; a request that misses prefills everything. With MKV​(P) the cache of the prefix and tfetch​=tmove​(MKV​(P)) over the path from the tier,

thit​=tfetch​+tsuffix​(P,Sinput​)

Fetching wins on latency when thit​<tprefill​. Neglecting the latency and per-block terms of tmove​, that is the condition that the path delivers faster than a break-even rate:

BWbe​=tprefill​(Sinput​)−tsuffix​(P,Sinput​)MKV​(P)​

When the prefix is the whole prompt only the pass over the last position remains; neglecting it, this reduces to MKV​/tprefill​, the comparison of transfer time with recompute time that the scheduler of [MOONCAKE] makes, written with the quantities of this model. The break-even rate is also the rate at which a prefill replica produces cache, which gives the condition a direct reading: a fetch pays when the path moves cache faster than the accelerators can make it.

A fraction p of requests hit. Two rules decide what a hit does. Under the latency rule a hit is served from the cache only when that is faster; under the always rule every hit is fetched. The expected time of the prefill phase, which replaces tprefill​ in the TTFT of e2e.md §2, and the expected device time of prefill per request are

E[tfirst​]=p⋅tfirst,hit​+(1−p)⋅tprefill​E[twork​]=p⋅twork,hit​+(1−p)⋅tprefill​

RuleHit served from the cache whentfirst,hit​twork,hit​
Latencythit​<tprefill​min(thit​,tprefill​)tsuffix​ if served from the cache, else tprefill​
Alwaysevery hitthit​tsuffix​

The fetch itself is a copy and uses no accelerator compute, so the device time of a hit is the suffix alone. With Bpf​=1, E[twork​] replaces tprefill​ in the prefill service rate of §4, which is how reuse raises throughput per device: the prefill pool does less work per request. The latency rule gives up that saving whenever it skips a fetch; the always rule keeps it at the price of a slower first token on a slow path.

The fetch path as a second limit. A fetched prefix costs no accelerator compute, but it occupies the path. A prefill replica whose path delivers Rfetch​ bytes per second cannot serve more than μfetch​=Rfetch​/(p⋅MKV​(P)) requests per second when hits are served from the cache, so the prefill service rate of §4 is μp​=min(1/E[twork​],μfetch​). The limit binds when the suffix is short: as the prefix approaches the whole prompt the device time per request falls toward zero, and the path alone sets how many requests a replica can take.

Worked case. The deployment of §1 with a 36,864-token prompt of which 32,768 tokens are cached, fetched at 26 GB/s. A miss prefills in 1.47 s. A hit fetches 10.74 GB in 0.41 s and prefills the suffix in 0.21 s. The break-even rate is 8.5 GB/s. At a hit rate of 0.9 the expected device time of prefill falls by 77%, which alone would let a replica serve 2.98 requests per second; the fetch path carries the prefixes of 2.69, so the path is the limit and the replica serves 2.69.

8. Warm Tiers and Sessions

Warm memory is described as an ordered list of tiers on a host, fastest first. A tier has a capacity per host Ctier​, a read rate, a write rate, a latency, and the path of §2 that leads from it to the accelerators. A fetch uses the read rate as the first stage of that path and a store uses the write rate. Host DRAM and CXL memory are tiers of this kind. For CXL memory, [CXL-MELODY] reports device rates of 18 to 52 GB/s at load latencies of 214 to 394 ns, and about 600 ns behind a switch; [BELUGA] reports about 750 ns through its switch. A switch is one more stage in the path and adds its latency. Because every such path ends in the same host stages, adding devices to a tier cannot raise the rate above them.

Cold tiers use the same description. A flash tier has several drives in parallel, a latency of tens of microseconds and a write rate of its own; a remote store has a network stage at the head of its path. Neither needs a change to §2, and because both end in the same host stages, eight drives at 14 GB/s each still deliver only the host rate into the accelerators.

Sessions. Let a decode replica hold Nact​ sequences in hot memory (kv.md §6) and let a fraction fidle​ of sessions be idle at any moment, waiting on a user or a tool with a cache that is not being decoded. Let MKV​(S) be the cache of one session at its context length S and nh​ the replica’s share of hosts, its devices divided by the devices per host. A replica of whole hosts has all of their memory; a replica smaller than a host shares that host’s tiers and host path with the other replicas on it and is given its proportional share, so nh​<1 and eight one-device replicas on an eight-device host together park what the host holds, not eight times that. A tier holds a whole number of idle caches, and the replica then serves

Nparked​=⌊MKV​(S)nh​⋅Ctier​​⌋Nsessions​=min(1−fidle​Nact​​,Nact​+Nparked​)

sessions on average. The first term is what the idle fraction calls for: Nact​ sequences running at once. The second is the room for all caches together: an idle cache may stay in hot memory while a slot is free there, and only the overflow is parked. Requiring every idle cache to leave hot memory would replace it by the stricter Nparked​/fidle​. A session that resumes pays one fetch of its cache and the suffix prefill of its new turn, which is §7 with a hit rate of one.

Several tiers. Idle sessions fill the tiers in a given order, warm before cold, which is the fastest-first rule the hot placement uses. Each tier j holds a whole number of caches, so Nparked​=∑j​⌊nh​⋅Cj​/MKV​(S)⌋, and the fetch a resuming session pays is that of the tier it sits in. The mean over the parked sessions weights each tier by the sessions it holds. Which session is moved to a colder tier, and after how long, is a policy this model does not contain: it counts where sessions fit, not when they move.

Worked case. For the deployment of §1 at 36,864 tokens, 80 sequences are active in hot memory and 2 TB of host DRAM holds 165 idle caches. With 80% of sessions idle the replica serves 245 sessions, limited by the tier: 49 are running, 31 idle caches stay in hot memory and 165 are parked. With 95% idle and the server’s eight 3.84 TB flash drives as a second tier, the cap moves from 245 sessions to 1,600: 165 parked in DRAM and 1,355 on flash, each resumed in under half a second because the host path, not the drives, sets the rate.

9. Limits

  • Not validated against measurement. The decode step that every result here builds on is compared with measured time per output token elsewhere. Time to first token, the handoff, pool sizing, prefix reuse and session counts are not validated. A comparison of the model’s time to first token with public measurements of disaggregated deployments at low concurrency did not meet its two acceptance tests (the change with prompt length within 15%, and absolute values within 25% after fitting one scheduling constant per serving stack), and those measurements themselves differ by up to 3.5 times between runs that share prompt length, prefill shape and concurrency, which is wider than either tolerance. So these are derived quantities whose inputs are the decode and prefill models and the published component rates cited in §1 to §3. Read them as what the stated assumptions imply, and calibrate the host-path rate and the delivered link rate on the platform in question before relying on an absolute time.
  • No queue. Every result is a steady-state mean. Waiting time enters only through the utilisation cap of §4 and through a scheduling term in the TTFT of e2e.md §2.
  • Hit rate and idle fraction are inputs. Predicting them needs a workload model and an eviction policy, which are out of scope. Results that depend on them are reported as sweeps.
  • The handoff is priced for a request that prefills its whole prompt. On a hit the prefill phase is shorter, so less of the transfer can overlap it; this second-order effect is not modelled.
  • Reuse is priced for unbatched prefill, because the suffix of §6 is a single request.
  • A batched prefill hands off one cache at a time. With Bpf​>1 the prefill time is that of the batch, but the handoff is still priced for one sequence’s cache with the link to itself; the caches of one batch contending for the link is not modelled.
  • Sessions are counted against what hot memory holds, not against the priced batch. Nact​ in §8 is the number of sequences the replica can keep in hot memory, which can exceed the decode batch the step time was computed for; the session count then assumes more sequences are held than are decoded at once.
  • Contention for the host’s processors is one factor. ηbusy​ slows a transfer on a busy host. The reverse effect, a transfer slowing the decode loop by taking processor time, has no term: there is no measurement to size it.
  • A prefix cache kept in hot memory is not modelled. It would compete with the caches of running sequences for the capacity of kv.md §6.
  • Cold tiers have no demotion policy. Which idle session sits in which tier follows the fill order of §8 alone, and the time a session waits before it is moved is not modelled. No write rate is sourced for flash, so a store to it is priced at its read rate.
